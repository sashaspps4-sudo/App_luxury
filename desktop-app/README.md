# Luxury Mailer Desktop

Стартовый интерфейс десктопного мейлера на Tauri 2, React и TypeScript.

## Запуск интерфейса в браузере

```powershell
npm install
npm run dev
```

## Запуск desktop-приложения

```powershell
npm run tauri dev
```

Для запуска профилей нужен Node.js в PATH. Перед первым запуском установите браузер и зависимости:

```powershell
npm run browsers:setup
```

На странице «Обзор» добавляйте профили кнопкой «+» и убирайте крестиком на карточке,
затем нажмите «Запустить рассылку». Браузеры сразу открывают `https://gmail.com/`.
Пустое поле прокси означает прямое подключение. Можно сочетать профили с прокси и без него.
Поддерживаются `socks5://login:password@host:port`,
`host:port` и `host:port:login:password`. В URL специальные символы логина и пароля
нужно кодировать.
У каждого профиля отдельная папка `browser-profiles/profile-N` в каталоге данных приложения;
входы и cookies сохраняются при закрытии. «Остановить» закрывает браузеры.
Статусы окон, этапы отправки и ошибки отображаются в обзоре. После «Аккаунты готовы»
и сохранения входящих/объявлений запускается первоначальная отправка писем.
В браузерном предпросмотре запуск недоступен — используйте desktop-приложение.

Список профилей и прокси сохраняется автоматически на компьютере пользователя.
В desktop-приложении файл `profiles.dat` защищён Windows DPAPI; в браузерном
предпросмотре используется локальное хранилище браузера. У профилей постоянные
номера: удаление одной карточки не меняет папки и сессии остальных.
Крестик удаляет карточку, сохранённый прокси и папку браузерной сессии с диска,
включая cookies и данные входа. Удаление доступно после закрытия браузеров.
Добавленный после удаления профиль получает новый номер и отдельную сессию.

Проверка браузеров и SOCKS5 с авторизацией: `node --test browser-runtime/worker.test.mjs`.

Каждый профиль запускается в отдельном Node.js-процессе Playwright. Закрытие или сбой
одного воркера не завершает остальные. При старте native-часть читает выбранный
сохранённый конфиг и фиксирует снимок с `runId`, названием и режимом. Полный снимок
передаётся каждому воркеру через stdin; в статусы и журналы секреты конфига не выводятся.
Изменения настроек относятся к следующим запускам.

«Аккаунты готовы» отправляет проверку каждому работающему воркеру. Готовность
подтверждается наличием открытой вкладки HTTPS на точном домене `mail.google.com`
с путём `/mail/u/<номер>/`. Это проверка URL, без проверки содержимого почты.
Вход на `accounts.google.com` готовность не подтверждает. Можно войти и повторить
проверку. Выход из почты или закрытие последней вкладки Gmail сбрасывает готовность.
После успешной проверки всех открытых аккаунтов каждый воркер переводит свой
аккаунт в `#inbox`, затем собирает метаданные всех страниц через поиск
`in:inbox` (включая разные категории входящих) и возвращает вкладку в `#inbox`.
Сохраняются устойчивые ID цепочки и последнего письма, без открытия писем и
изменения статуса прочтения. Адрес аккаунта проверяется по заголовку Gmail.
Отправители с домена `google.com` и его поддоменов исключаются.
Отпечаток сохраняется на сервере и сверяется с известными ID по пользователю и
почтовому аккаунту. Для больших списков используется загрузка частями. Ошибка
сбора или сохранения останавливает подготовку до запроса парсера. Поддерживается
до 20 000 цепочек / 400 страниц на профиль; превышение вызывает явную ошибку.
После сохранения выполняется сверка отправителей с объявлениями пользователя.
Однозначные совпадения сохраняются кандидатами для будущего автоответчика,
неоднозначные — для проверки. В консоли отображаются количества совпадений,
неизвестных отправителей и уже обработанных кандидатов. Отправка автоответов
пока не подключена.
Проверки DOM и воркеров: `node --test browser-runtime/inbox.test.mjs`.

После сохранения отпечатков всех открытых профилей приложение обращается к
`POST /v1/parser/batch` нашего API с текущей лицензией. Сервер запрашивает у
VVSPARSER одну общую партию: 10 объявлений на каждый готовый профиль. API-ключ,
площадка, страны и фильтры берутся из снимка конфига при запуске; изменения
настроек действуют со следующего запуска. `email=true` передаётся всегда,
категория не передаётся (все категории). Для каждой площадки передаются только
поддерживаемые ею фильтры из `vvs_requests.txt`.

Объявления без корректного email и повторяющиеся email исключаются. Результат
распределяется между профилями поровну, максимум по 10; нехватка отображается в
консоли. Данные объявлений сохраняются с текущим запуском в native-части.
Повторная проверка того же запуска получает сохранённую партию с сервера;
повторный запрос к VVS не выполняется. Для собственной базы парсер пропускается.
При ошибке парсинга можно повторить «Аккаунты готовы». После запуска очереди
повторный запуск тех же заданий блокируется. Режим воронки пока отправляет только
первое письмо; автоматические ответы остаются отдельным следующим этапом.

Перед запуском заполните «Темы писем»: одна непустая строка на вариант, с
`{item}`, `{name}`, `{price}`. Варианты темы ротируются независимо от строк текста
воронки. В рассылке используется выбранный HTML-шаблон (или Custom HTML),
подстановка значений экранируется. `{link}` до подключения провайдеров не заполняется.
HTML вставляется как отрисованное содержимое; исходники шаблонов не изменяются.

Новая таблица `outbound_jobs` хранит `pending`, `sending`, `sent`, `failed`,
`unknown`, время и ID подтверждения. Только новый попап текущего черновика и
подтверждённая запись в БД увеличивают счётчик отправок. Ошибка останавливает
очередь этого профиля. `unknown`/оставшийся после сбоя `sending` не переотправляются.
Собственная база адресов пока не подключена к отправке — используйте базу парсера.
Проверки отправки на локальных макетах Gmail (без реальных писем):
`node --test browser-runtime/sender.test.mjs`.

## Проверка production-сборки интерфейса

```powershell
npm run build
```

Авторизация по лицензии подключена к API; локальная сессия в Windows защищена DPAPI.
Счётчики первоначальных отправок отражают подтверждённые операции текущего запуска.
Счётчики ответов и автоответов пока остаются демонстрационными.
